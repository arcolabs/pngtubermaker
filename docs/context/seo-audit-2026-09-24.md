# SEO audit record — pngtubermaker.com — 2026-09-24

Successor to `seo-audit-2026-09-15.md`, which stays authoritative for the
canonical / trailing-slash / `/create` / lastmod findings it closed. This record
covers one defect class that the earlier audit's method could not see, and the
ratchet added so it cannot recur.

## Defect: three live pages were unreachable

`/pngtuber-models`, `/obs-pngtuber`, and `/picrew-pngtuber-maker` were created
by the Arcops organic Work loop and merged in PRs #5, #6, and #7 (commits
`6d6522ee`, `7ab08970`, `e7c613ee`, all Arcops-authored). All three returned
**200 with real content** throughout — this was never a broken-page bug.

They were nonetheless effectively unpublished, for two independent reasons:

| Surface | State before the fix |
|---|---|
| sitemap | absent. `staticRoutes` held 14 routes x 12 locales = 168 entries, exactly what live served |
| nav / footer | absent. No `Footer.tsx` link in either the desktop or the mobile block |
| inbound links | `/picrew-pngtuber-maker` had **zero** inbound links anywhere in the app; `/obs-pngtuber` only from picrew; `/pngtuber-models` only from those two |

The third row is the one that matters. The three pages linked *out* to
established pages (`/vtuber-maker`, `/free-pngtuber-maker`,
`/guides/how-to-make-a-pngtuber`), so the graph was a closed chain whose head
was itself unreachable. A crawler that starts from the homepage or the sitemap
could never arrive at any of them. Inbound link equity flowed out and nothing
came back.

### Why the 2026-09-15 audit missed it

That audit enumerated **sitemap -> URLs** and then probed each URL's status,
canonical, and head. That direction is blind to this defect by construction: a
page absent from the sitemap is never enumerated, so it is never probed, and its
absence is not itself a finding. `seo-verify.sh` inherited the same shape — it
asserted sitemap *properties* (no trailing-slash locs, no `/create`, no
`<lastmod>`) but never *coverage* against the routes that actually ship.

A method that only ever walks down from an index cannot report that the index is
incomplete. Checking that needs the opposite direction: filesystem -> sitemap.

## Fix

Three parts, all in one change.

1. **Sitemap registration** (`apps/web/app/sitemap.ts`): the three routes added
   to `staticRoutes`, plus a new `localized?: boolean` field. Emitted count went
   168 -> **171**, verified on the prerendered artifact.

2. **Footer links** (`apps/web/components/layout/Footer.tsx`): added to *both*
   the desktop grid block and the `md:hidden` mobile block — editing only one
   would have left mobile users and mobile-UA crawlers without the inbound edge.
   Labels added to `messages/*/footer.json` in all 12 locales (18 -> 21 keys).

3. **Coverage ratchet** (`docs/context/seo-coverage-check.sh`), wired into
   `.github/workflows/pr.yml` after the production build so it inspects the
   artifact that actually ships.

### The `localized: false` decision

These three pages are English-only **by construction**: their hero and prose
copy is hardcoded in the route file, they never call `getLandingPage()`, and
there is no `messages/<locale>/landing-<slug>.json` for them. Only the shared
sections (FAQ, testimonials, footer) localise, because those read from
`messages/`. Measured on live: `/ja/pngtuber-models` returned 200 with an
identical English `<h1>` while its FAQ section *was* Japanese, and the page
canonicalised to the EN URL.

So a naive registration would have emitted 36 more entries (12 locales x 3
pages) advertising translations that do not exist. That is the fake locale fleet
`seo-audit-2026-09-15.md` already flags as **an open policy question owned by
Kai**, and silently expanding it would have preempted that decision in the wrong
direction. Instead `localized: false` emits one EN entry with only an
`x-default` alternate, which matches what the pages' own canonicals already
declare. The locale variants stay reachable and still canonicalise correctly;
they are simply not advertised.

Footer labels are English in every locale for the same reason: a translated label
would promise localised content the destination page does not have. This is
consistent with existing precedent — measured on `messages/de/footer.json`, **16
of its 18 keys already carry English values**, including `twitchAvatarMaker:
"Twitch Avatar Maker"` and `vtuberMaker: "VTuber Maker"`. The three new labels
were verified to be byte-identical across all 12 locale files (1 distinct value
each).

### Manifest hash

`apps/web/scripts/i18n-translate.ts` hashes each `messages/en/*.json` into
`messages/.manifest.json` and, when a namespace hash differs, retranslates the
**whole namespace** and overwrites the target file wholesale. Editing
`en/footer.json` therefore made the stored hash stale (`f4b913b5` ->
`06b95c8e`), and the next legitimate translate run would have retranslated all
21 footer keys in 11 locales: churning 18 good translations and replacing the 3
deliberate English labels with machine translations pointing at English-only
pages. The hash is synced in this change. This is a cache key, not a build
validation — nothing fails without it, which is exactly why it needs doing by
hand.

## Verification

Method: build the real artifact, then serve it and probe as a crawler would.
A prerendered HTML file does not exist for these routes (they are
server-rendered), so the artifact check covers the sitemap and the served-HTML
check covers the links.

| Check | Result |
|---|---|
| `bun run check` (Biome, 578 files) | pass |
| `bun run build` | pass, 327 static pages |
| emitted sitemap `<loc>` count | **171** (was 168) |
| locale variants of the three EN-only routes | **0** |
| hreflang alternates on each new entry | **1** (`x-default`), not 12 |
| `href="/pngtuber-models"` occurrences on served `/vtuber-maker` | **2** (desktop + mobile) |
| same for `/obs-pngtuber`, `/picrew-pngtuber-maker` | **2** each |
| all three pages served | HTTP 200 |
| `seo-coverage-check.sh` on the fixed state | 25 checks, 25 PASS, exit 0 |
| `seo-coverage-check.sh` on a synthetic pre-fix sitemap | **exit 1**, naming exactly the 3 missing routes |
| production base URL | Dockerfile `ARG NEXT_PUBLIC_APP_URL` has no default; `sitemap.ts` falls back to `https://pngtubermaker.com`. `.env.local` is gitignored, so the local `http://localhost:4000` base cannot ship |

The negative test matters as much as the positive one. A ratchet that cannot fail
is not a gate, so it was run against a synthetic 168-entry sitemap
(`SEO_SITEMAP_FILE=...`, which exists for exactly this) and confirmed to exit 1
and name all three routes. The real build artifact was not mutated to test it.

### Bugs found in the ratchet itself while testing it

Worth recording because each one would have made the ratchet look green while
checking nothing:

- `${f#$MAIN_DIR/}` uses the variable as a **glob pattern**, and `MAIN_DIR`
  contains `[locale]` — a character class that never matched literally, so no
  prefix was stripped and raw filesystem paths were compared against sitemap
  paths. Fixed by quoting: `${f#"$MAIN_DIR"/}`.
- The root sitemap `<loc>` carries no path component at all
  (`http://host`), so stripping the host left an empty string where `/` was
  meant, and the homepage check reported 0. Normalised `^$` -> `/`.
- The showcase group root collapsed to the bare string `page.tsx` and was then
  dropped by the homepage filter, so **`/showcase` was never checked at all**.
  Fixed by stripping per source directory, and by adding a self-audit that
  asserts the enumeration contains known routes (`showcase`, `pricing`,
  `vtuber-maker`) so a future directory rename fails loudly instead of quietly
  checking nothing. That self-audit immediately caught this bug plus a
  `%/page.tsx` strip that did not match a filename with no leading slash.
- `/login` was in the exclusion list but sits outside both enumerated
  directories, so the entry was dead — it read as if it were being checked.
  Removed, with the scope boundary documented instead.

## Not fixed here

- **`/showcase` is a second orphan, of the same class, and is still live.** Found
  while extending the ratchet to cover the link half of discoverability (check 6).
  Measured on production 2026-09-24: it is in the sitemap at all 12 locales
  (12 of the 168 prod `<loc>`s), `GET /showcase` returns 200, and crawling all 14
  EN sitemap surfaces for navigational `href`s found **zero** inbound links to
  it — the only inbound was its own `<link rel="canonical">` self-reference,
  which is not navigation. It is not a stub either: `showcase/page.tsx` is a
  354-line `"use client"` component with its own round/expression configuration,
  so this is real content with no path to it. Unlike the
  three Arcops-loop pages it predates this work and is not their responsibility,
  and linking it is a product/navigation decision (what label, which footer or
  header column, whether it deserves global-chrome space at all), so it is
  recorded as `LINK_EXEMPT` debt that prints `WARN` on every run rather than
  silently shipped. Its exposure is smaller than the three pages' because those
  had no sitemap entry either, while `/showcase` is at least crawler-discoverable
  through the sitemap; but sitemap-only discovery earns no internal link equity
  and no user path. If the intent is that this page should never be reachable
  from chrome, it should come out of the sitemap instead.
- **The locale fleet question is still open and still Kai's** (see
  `seo-audit-2026-09-15.md` §"OPEN POLICY"). This change deliberately does not
  expand or shrink it; the three new pages are EN-only for now.
- **`components/sections/ExplorePages.tsx` is rendered by nothing.** Grepping the
  app for `ExplorePages` matches only its own definition. It is dead code holding
  a curated link list. Left alone: out of scope for a discoverability fix, and
  deleting it is a separate decision. Worth noting here only because it is the
  one place holding a curated internal-link list that is *not* global chrome, and
  it does not list `/showcase` either, so reviving it would not close the orphan.
- **No `LANDING_SLUGS` entry was added for the three pages**, deliberately. That
  registry enumerates slugs whose copy loads from
  `messages/<locale>/landing-<slug>.json` via `getLandingPage()`, which throws
  when the file is absent. These pages hardcode their copy, so registering them
  there would break them. Two page styles now coexist; the ratchet guards the
  property that matters (is every public route listed) without requiring either
  style to adopt the other's registry.

## Environment traps (additions to the 2026-09-15 list)

- Route group roots yield the bare filename `page.tsx` after the directory is
  stripped, and both the `(main)` group root (homepage) and `showcase` produce
  it. Stripping one prefix for both conflates them silently.
- `[locale]` and `(main)` in a path break `${var#pattern}` stripping, because
  bash treats the pattern as a glob. Quote the variable.
- Counting occurrences of a substring in minified HTML with `grep -c` counts
  **lines**, and the served HTML is a single line — it reports 1 no matter how
  many occurrences exist. Use `grep -o ... | wc -l`.
- `cmd | tail -3` makes `$?` belong to `tail`. A failing `bun run check` piped
  through `tail` reported exit 0. Redirect to a file and check `$?`.
- A production build of this app takes ~16s and prerenders 327 pages; that is
  normal here, not a no-op build.
- Serving the build with `timeout N next start &` and killing the tracked PID
  leaves the **`next-server` child alive** with the port still bound. Reclaim by
  PID from `ss -ltnp`, and verify with `ps -eo comm=` (matching on `args=`
  self-matches the checking command).
