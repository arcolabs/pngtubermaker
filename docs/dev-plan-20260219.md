### Task 1.1: Database Schema Update

**Priority**: P0
**Estimate**: ~2h
**File changes**: `database/schema.ts`, new migration

Update existing schema to support Credit system:

```
Changes:
- wallets table: rename `balance` (decimal) → `creditBalance` (integer)
  - Add `subscriptionCredits` (integer, monthly grant, resets)
  - Add `purchasedCredits` (integer, permanent, never expires)
  - Add `subscriptionCreditsExpiresAt` (timestamp)

- New: credit_transactions table
  - id, visibleId
  - userId (FK → user)
  - type: 'grant' | 'consume' | 'purchase' | 'expire' | 'refund'
  - amount (integer, positive = credit, negative = debit)
  - balance (integer, balance after transaction)
  - description (text)
  - metadata (jsonb, e.g. { taskType: 'avatar_generation', avatarId: '...' })
  - createdAt

- New: avatars table (rename from generatedAvatars)
  - id, visibleId
  - userId (FK → user)
  - name (varchar, user-given name)
  - prompt (text, original prompt)
  - style ('anime' | 'chibi')
  - status ('generating' | 'completed' | 'failed')
  - baseImageUrl (text, Midjourney output)
  - thumbnailUrl (text, compressed preview)
  - creditsUsed (integer)
  - metadata (jsonb)
  - createdAt, updatedAt

- New: avatar_expressions table
  - id
  - avatarId (FK → avatars)
  - type ('idle' | 'talking' | 'happy' | 'sad' | 'angry' | 'surprised')
  - imageUrl (text, transparent PNG on R2)
  - status ('pending' | 'generating' | 'completed' | 'failed')
  - creditsUsed (integer)
  - createdAt

- subscriptions table: add `monthlyCredits` (integer)
```

**Acceptance criteria**:
- `bun run db:generate` produces clean migration
- `bun run db:push` applies without error
- All existing tables preserved (non-breaking)

### Task 1.2: Credit Service Layer

**Priority**: P0
**Estimate**: ~3h
**New files**: `lib/services/credits.ts`

Core credit operations (server-side only):

```typescript
// Functions to implement:

getBalance(userId: string): Promise<{
  total: number;
  subscription: number;
  purchased: number;
  expiresAt: Date | null;
}>

consumeCredits(userId: string, amount: number, description: string, metadata?: object): Promise<{
  success: boolean;
  newBalance: number;
  error?: string;  // 'insufficient_credits'
}>

grantSubscriptionCredits(userId: string, amount: number, expiresAt: Date): Promise<void>

grantPurchasedCredits(userId: string, amount: number): Promise<void>

refundCredits(userId: string, amount: number, description: string): Promise<void>

expireSubscriptionCredits(): Promise<void>  // Cron job: expire unused monthly credits
```

**Key rules**:
- Consume subscription credits first (FIFO by expiry)
- All operations must be atomic (use DB transactions)
- Every credit movement logged to `credit_transactions`
- Balance must never go negative

**Acceptance criteria**:
- Unit tests for consume/grant/refund
- Atomic transaction ensures no double-spend
- `consumeCredits` returns `insufficient_credits` when balance < amount

### Task 2.1: Generation Service — Adapter Pattern

**Priority**: P1
**Estimate**: ~3h
**New files**: `lib/services/generation/types.ts`, `lib/services/generation/adapter.ts`, `lib/services/generation/mock-adapter.ts`

Create an adapter interface so we can swap between mock/Midjourney/NanoBanana:

```typescript
// types.ts
interface GenerationAdapter {
  generateCharacter(prompt: string, style: 'anime' | 'chibi'): Promise<GenerationResult>;
  generateExpression(baseImageUrl: string, expression: ExpressionType): Promise<GenerationResult>;
}

interface GenerationResult {
  status: 'completed' | 'failed';
  images: string[];  // URL array
  error?: string;
}

type ExpressionType = 'idle' | 'talking' | 'happy' | 'sad' | 'angry' | 'surprised';

// mock-adapter.ts
// Returns placeholder images after simulated delay
// Used for development until real APIs are integrated

// Future files (created when APIs provided):
// midjourney-adapter.ts  — Midjourney Niji for character generation
// nanobanna-adapter.ts   — Nano Banana Standard for expression editing
```

**Why adapter pattern**:
- **Unblocks all frontend/backend development** without real API keys
- When Midjourney/NanoBanana API docs arrive, just implement new adapter
- Can A/B test different providers later
- Easy to add fallback (if NanoBanana fails → try Flux Kontext)

**Acceptance criteria**:
- Mock adapter returns 4 placeholder images for `generateCharacter`
- Mock adapter returns 1 image per `generateExpression` call
- Simulates realistic latency (2-5s for character, 1-3s per expression)
- Adapter can be swapped via env var: `GENERATION_ADAPTER=mock|production`

### Task 2.3: Avatar Generation API

**Priority**: P1
**Estimate**: ~4h
**New files**: `app/api/avatars/generate/route.ts`

```
POST /api/avatars/generate
Auth: Required
Body: { prompt: string, style: 'anime' | 'chibi' }
Cost: 300 credits

Flow:
1. Validate auth + check credit balance ≥ 300
2. Consume 300 credits (atomic)
3. Create avatar record (status: 'generating')
4. Call adapter.generateCharacter(prompt, style)
5. Upload 4 candidate images to R2
6. Update avatar record with image URLs
7. Return { avatarId, images: [url x4] }

Error handling:
- If generation fails → refund 300 credits → set status: 'failed'
- If insufficient credits → return 402 with balance info
```

**Acceptance criteria**:
- Credits consumed before generation starts
- Credits refunded on failure
- Avatar record persisted in DB
- Returns 4 candidate images

### Task 2.4: Expression Generation API

**Priority**: P1
**Estimate**: ~4h
**New files**: `app/api/avatars/[id]/expressions/route.ts`

```
POST /api/avatars/[id]/expressions
Auth: Required (must own avatar)
Body: { expressions: ['talking', 'happy', 'sad'] }
Cost: 200 credits × expression count

Flow:
1. Validate ownership + credit balance
2. Consume credits (200 × count)
3. Create expression records (status: 'pending')
4. For each expression:
   a. Call adapter.generateExpression(baseImageUrl, type)
   b. Run background removal
   c. Upload transparent PNG to R2
   d. Update expression record (status: 'completed', imageUrl)
5. Return expression statuses

Streaming progress:
- Option A: SSE (Server-Sent Events) — send update as each expression completes
- Option B: Polling — client polls GET /api/avatars/[id] for status
- Recommendation: Option B (polling) for MVP simplicity
```

**Acceptance criteria**:
- Base image from avatar used as reference
- Each expression generated sequentially and saved
- Background removed automatically
- Credits refunded proportionally on partial failure
- Client can poll for progress
